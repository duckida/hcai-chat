# AGENTS.md - Coding Agent Guide for HCAI Chat

This document provides an overview of the codebase, architecture, and development environment for coding agents working on the **HCAI Chat** application.

## Project Overview
HCAI Chat is a modern AI-driven chat interface built with **Next.js (App Router)**, featuring real-time streaming, web search integration, an Agent Mode that runs code in per-user **E2B cloud sandboxes** (always available; users supply their own E2B API key in Settings), and an "Artifacts" system for displaying structured HTML content generated by the AI. It connects to the Hack Club AI proxy (`https://ai.hackclub.com/proxy/v1`).

## Tech Stack
- **Framework**: Next.js 16+ (App Router)
- **Styling**: Tailwind CSS v4, Shadcn UI, Lucide React, Framer Motion
- **Language**: JavaScript (ESM), JSX for components
- **API/Backend**: Next.js API Routes (Serverless)
- **Search Integration**: Exa AI via Hack Club proxy
- **Streaming**: AI SDK v6 (`ai` + `@openrouter/ai-sdk-provider`)
- **Content Rendering**: Streamdown (with cjk, code, math, mermaid plugins)
- **Code Quality**: Biome (Linting/Formatting)
- **Testing**: Vitest + React Testing Library + jsdom

## Key Architectural Concepts

### 1. Streaming Chat
The `/api/chat` route uses `streamText` from the AI SDK with OpenRouter provider. It emits SSE events (`data: ...` format) with text deltas, reasoning deltas, tool call deltas, search results, and usage metrics. The client parses these in `streamChatCompletion`.

### 2. Tool Registry (`src/lib/tools.js`)
All tools defined in `TOOLS` array with JSON Schema parameters. Each tool has a corresponding executor:
- `web_search` — calls Hack Club AI's Exa proxy (`/proxy/v1/exa/answer`), returns answer + citations
- `javascript_calculator` — evaluates arithmetic using tokenizer → Shunting-yard → RPN
- `execute_code` / `run_command` — sandbox tools, only included when agent mode is enabled

Both `/api/chat` (via AI SDK native tool calling) and `/api/tools` (standalone endpoint) use the same `executeTool` function. Agent sandbox tools are routed through `sandbox-executor.js`.

### 3. Context Usage Counter
A ring chart in the header (`ContextUsage.jsx`) shows how much of the model's context window is consumed. The model list is fetched from `/api/models` on mount in `ChatLayout.jsx`, which populates a `contextWindowMap` keyed by model ID (from each model's `context_length` field). The API route emits a `usage` event at the end of each turn with `inputTokens`, `outputTokens`, and `reasoningTokens`; `page.js` stores the cumulative total (`inputTokens + outputTokens`) as the conversation's `contextUsage`. This total includes previous turns, thinking/reasoning, and tool call/output tokens because they are all part of the request history or completion. While a response is streaming, `page.js` increments a live character-based estimate so the ring fills progressively, then snaps to the exact server-reported total when the `usage` event arrives. The persisted value is restored on page load and on conversation switch, and usage is always attributed to the conversation that initiated the request (even if the user switches away mid-stream). The ring changes color at 75% (yellow) and 90% (red).

### 4. Artifacts System
The AI emits HTML inside ```html fenced code blocks. `ArtifactPanel` renders these in an iframe (preview tab) or syntax-highlighted (code tab). The system supports streaming (unclosed fences show a loading state).

### 5. Agent Mode
Agent Mode enables the AI to execute JavaScript code and shell commands in a per-conversation **E2B cloud sandbox** billed to the user's own E2B account. **Always available** — no feature flag gates it. Users must store their own E2B API key (`e2b_...`) in Settings; without a key the agent toggle is disabled with a tooltip and sending with agent mode shows a toast error. A killed sandbox loses its files (accepted trade-off); E2B charges the user's account for sandbox usage.

**Sandbox (`src/lib/sandbox.js`):**
- E2B SDK `Sandbox` clients cached in a `Map` keyed by `conversationId`; `Sandbox.create({ apiKey, timeoutMs, metadata })` or `Sandbox.connect(sandboxId, { apiKey })` for reconnects
- **Lazy-loaded**: `e2b` imported dynamically inside `ensureLoaded()` on first use, never at module load — prevents OOM during `next build`
- Per-user `apiKey` passed on every call (never stored server-side); `conversationId` passed via `metadata`
- `/workspace` created via `files.makeDir("/workspace")` on every create/connect (E2B templates have no `/workspace` by default; `commands.run` with a missing `cwd` fails)
- 30s execute / 120s command timeouts with a client watchdog that kills the command (`handle.kill()`) while the sandbox stays alive
- Max 3 concurrent sandboxes with LRU eviction; 5-minute idle cleanup via periodic sweep; 10-minute sandbox timeout extended on each use (`refreshTimeout`)
- `isSandboxGoneError` ("sandbox was killed", "reached its end of life", "sandbox not found", `SandboxNotFoundError`) → evicts cached client and retries once with a fresh sandbox
- `destroySandbox(conversationId, { apiKey, sandboxId })` kills the cached client, or falls back to remote `Sandbox.kill(sandboxId)` (serverless cold-cache destroy); `destroyAllSandboxes` iterates cached keys
- `listFiles` returns files under `/workspace` (depth 3, hidden files/node_modules filtered), `readFile` is path-traversal-safe via `resolveWorkspacePath`

**Tool flow:**
- Agent tools (`execute_code`, `run_command`) are injected into the AI SDK tool loop when `agentMode` is set in the chat route
- The chat route dynamically imports `sandbox-executor.js` only when a sandbox tool is invoked; per-user key and `sandboxId` are plumbed from the request body
- The chat route emits `sandbox_result` SSE events with tool, code, stdout, stderr, exit code, and sandboxId; non-streaming fallback returns the same shape in `sandboxResults`
- The client tracks streaming sandbox calls in `streamingSandboxTools` state (live in `StreamingMessage`); `onSandboxResult` persists the `sandboxId` back into the conversation (IndexedDB)
- A `CompletedSandboxFiles` section at the bottom shows generated file pills after streaming completes
- File downloads use a two-step flow: POST `download_token` (mints a single-use 60s token) then GET `/api/sandbox?action=download&token=...` — the E2B key never appears in the URL
- Settings: "Show Sandbox Input" (`show_sandbox_code`) and "Show Sandbox Output" (`show_sandbox_output`) toggles live in the Sandbox section and gate the code/command block and stdout/stderr sections; "Show Thinking" controls thinking block default state

**SSE Streaming Resilience:**
- Caddy proxy advertises HTTP/3 via `alt-svc: h3=":443"; ma=2592000`, causing `ERR_QUIC_PROTOCOL_ERROR` on long-lived SSE streams during tool execution
- Server sends `X-Accel-Buffering: no` and `Alt-Svc: clear` headers
- Keepalive comment (`: keepalive\n\n`) sent every 5s to prevent proxy idle timeout
- Client-side fallback: on SSE stream failure, retries with `stream: false` (JSON response) and pipes through `onChunk`
- `send()` function uses `controller.desiredSize === null` guard instead of silent try-catch to prevent stuck "Running" state

### 6. State Management & Persistence
- **Conversations**: IndexedDB via `src/lib/db.js` with localStorage migration fallback. Each conversation persists its `sandboxId` so sandbox reconnects survive page reloads.
- **Settings**: localStorage keys for API key, E2B key (`e2b_api_key`), model selection, toggles (`thinking_enabled`, `agent_mode_enabled`, `show_sandbox_code`, `show_sandbox_output`, `show_metrics`, `show_thinking`), theme, metrics, etc.
- **Context**: Conversation title, messages, model, and artifact panel state are persisted per-conversation.
- **Hydration safety**: Values read from localStorage (e.g. `hasE2bKey`) must be initialized in state (server-safe default) and populated in the mount `useEffect` — reading storage during render causes hydration mismatches (e.g. `disabled` attribute differences).

### 7. Search Page
`/search?q=...&search=true` renders the main chat page with an auto-sent initial query using web search enabled. Handled via `src/app/search/page.js`.

## Testing
The project uses **Vitest** and **React Testing Library** with jsdom environment.

### Test Structure
- `src/lib/__tests__/`: Tests for utility functions and business logic.
- `src/components/chat/__tests__/`: Tests for React components.
- `src/app/api/*/__tests__/`: Tests for Next.js API route handlers (route.test.js per endpoint).

### Commands
- `npm run test`: Run test suite (single run)
- `npm run test:watch`: Run in watch mode
- `npm run test:coverage`: Run with v8 coverage

### Key Guidelines
- **Model references in tests**: Use `qwen/qwen3.6-flash` for consistency. Note: the app's default chat model is `xiaomi/mimo-v2.5`.
- **Mocks**: Global mocks in `vitest.setup.jsx` for fetch, localStorage, navigation, theming, animation.
- **Isolation**: Use `vi.resetModules()` and `vi.useFakeTimers()` for tests relying on stateful module variables.
- **Sandbox tests** (`src/lib/__tests__/sandbox.test.js`, 21 tests): mock the `e2b` module with a static `vi.mock("e2b", ...)` factory, use static `import * as sandbox from "@/lib/sandbox"`, and reset state in `beforeEach` with `await sandbox.destroyAllSandboxes()` + `vi.clearAllMocks()` + re-setting `Sandbox.create/connect/kill` mock implementations. Do NOT use `vi.resetModules()` with mocked `e2b` — dynamic re-evaluation of a mocked module fails ("Cannot destructure property 'Sandbox'..."). Note `vi.clearAllMocks()` keeps `mockResolvedValue`/`mockImplementation` settings.
- **Known failures**: 8 `streamChatCompletion` tests in `src/lib/__tests__/api-client.test.js` fail (`describe.sequential` describe block) — pre-existing, unrelated to the sandbox work.

## Development Workflow

### Getting Started
1. `npm install`
2. `npm run dev`

### Code Quality
- `npm run lint` — Biome check
- `npm run format` — Biome format --write

### Coding Guidelines
- **Components**: Functional components with hooks. Shadcn UI patterns.
- **API Communication**: Use `src/lib/api-client.js` abstractions.
- **Styling**: Tailwind CSS exclusively, use `cn()` utility for conditional classes.
- **Error Handling**: API routes return structured errors, client parses via `getErrorMessage`.
- **No comments**: Keep code self-documenting; avoid inline comments.
